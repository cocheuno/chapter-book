## 1. Security and correctness: fix before registration opens

| # | Severity | Finding |
| --- | --- | --- |
| S1 | **High** | Anyone who knows an invited email address can claim that invite |
| S2 | Medium | A database error blanks the GoDaddy homepage |
| S3 | Medium | Grok's sign-in service can still sign people in to production |
| S4 | Medium | No security headers (clickjacking, no CSP) |
| S5 | Medium | Editor HTML allows positioning styles on public pages |
| S6 | Medium | The founder path is still open on an empty database |
| S7 | Low | Public page views write to the database, and deleting everything re-seeds samples |
| S8 | Low | The public feed and images cannot be cached |
| S9 | Low | Migrations run on every Vercel build |
| S10 | Low | Some queries are not scoped by chapter |
| S11 | Low | CSV exports are open to spreadsheet formula injection once the public can type names |

### S1. Anyone who knows an invited address can claim the invite (High)

- `loadMember` accepts the newest pending invite whose email matches the signed-in user (`src/lib/crm/member.ts:89-110`).
- Anyone can create an account. `src/lib/auth/server.ts:215` turns on Better Auth's email/password sign-up with no `disableSignUp` and no email verification.
- The invite token is only used by the browser, to fill in the form (`src/routes/login.tsx:36-67`). The server never checks it.

So anyone who knows an invited address can post to `/api/auth/sign-up/email` with it during the 14-day invite window and receive the invited role, **including admin**. Pastors' and professors' addresses are usually public. The same trick also blocks the real invitee, whose email is now taken.

Fix:

- Accept an invite only through a server function that takes the **token**. It should find the invite by `token_hash` and check that it matches the signed-in user's email. Remove the email-only branch from `loadMember`.
- Close open sign-up in the auth layer. Better Auth can do this with a `hooks.before` check on `/sign-up/email` that requires a valid invite token, or with `databaseHooks.user.create.before` rejecting any new user without a matching, unexpired invite. The founder path (S6) is the only other way in.
- Add a test that fails if sign-up works without a token.

### S2. A database error blanks the GoDaddy homepage (Medium)

On any error, `loadPublishedSite` returns an empty site with HTTP 200 (`src/lib/crm/site.ts:127-150`). The embed script then empties the title, tagline, and about text, and writes "Nothing posted yet." into every list (`public/embed/chapter-site.js:89-101`). A short Neon outage erases the live homepage for as long as it lasts.

Fix: return **503** from `/api/public-site` when the read fails. The embed's `catch` already leaves the GoDaddy markup in place. Do the same for `getPublicPage` (`site.ts:532`): it turns every error into "That page is not published."

### S3. Grok's sign-in service can still sign people in to production (Medium)

- `grokClientId` falls back to a built-in preview client (`src/lib/auth/server.ts:81-86`). That means the Google/X buttons, which go through Grok's sign-in service, stay live whenever auth is on.
- `accountLinking.trustedProviders` links an identity from that service to an existing account by email, with `requireLocalEmailVerified: false` (`server.ts:196-205`).
- Whoever runs that service is therefore trusted with your operators' identities.

The first review already said these buttons are not the chapter door. Before live payments, turn the service off in production, or take it out of `trustedProviders`. Keep it for the Grok Build preview if Grok needs it.

### S4. No security headers (Medium)

Neither `vercel.json` nor the server middleware sets any security headers:

- no `Content-Security-Policy`
- no `frame-ancestors` / `X-Frame-Options`
- no `Strict-Transport-Security`
- no `Referrer-Policy`

Without them, another site can frame `/login` and the future register page (clickjacking).

Add the headers in a Nitro middleware under `server/middleware/` or in `vercel.json` `headers`. Start with:

- `frame-ancestors 'none'`. GoDaddy reads the feed with `fetch`; it does not frame the book.
- HSTS and `Referrer-Policy: strict-origin-when-cross-origin`.
- A **report-only** CSP. TanStack Start's hydration scripts need nonces before a strict CSP can be enforced.

When Stripe arrives, the CSP needs `form-action 'self' https://checkout.stripe.com`.

### S5. Editor HTML can position elements on public pages (Medium)

The sanitizer (`src/lib/crm/announcement-html.ts`) is careful and well tested. It blocks `url()`, `expression()`, `javascript:`, event handlers, and dangerous tags. But its `style` filter still allows `position: fixed`, `z-index`, and `opacity`.

A stolen editor login could lay a fake "Pay here" link over the conference page. Once the page takes money, that is worth closing. The fix has to keep `<section>` HTML working on every public field, including the register page (section 7):

- Allow a short list of style properties: `text-align`, `color`, `background-color`, `font-weight`, `font-style`, `margin`, `padding`, and `width` on images.
- Put `contain: paint` on the `.announcement-html` wrapper. Everything inside it, even `position: fixed`, is then clipped to the copy's own box and cannot cover the page.
- On the register page, the app draws the form, prices, and Pay button **outside** the editor's copy blocks.

### S6. The founder path is still open on an empty database (Medium)

`getLoginState` and `bootstrapChapter` (`src/lib/crm/member.ts:112-153`, `src/lib/crm/operators.ts:31-40`) make the first person to sign up on an empty database the admin. That was right on day one.

Later, it is risky. A Vercel preview pointed at a fresh Neon branch, or a wiped database, hands admin to the first visitor. Two first sign-ups at the same moment can also create two chapters, and the public pages read the older one.

Fix: allow the founder path only for the address in a host variable such as `FOUNDER_EMAIL`. The name goes in `.env.example`; the value stays on the host.

### S7. Public page views write to the database (Low)

`loadPublishedSite` (`site.ts:127`) and `getPublicPage` (`site.ts:448`) run `ensureSiteContent`, `backfillSlugs`, and `backfillConference` on every anonymous request.

`seedSite` also re-inserts the whole sample shelf whenever `site_items` is empty (`src/lib/crm/site-seed.ts:164-167`). If an editor deletes the last item, the samples come back on the next page view, including the sample conference card.

Fix: move the backfills into a migration, and seed only when the chapter is created. Public reads should only read.

### S8. The public feed and images cannot be cached (Low)

The feed sends `Cache-Control: no-store` (`src/lib/crm/public-cors.ts:21`), and the embed adds `?t=Date.now()` (`chapter-site.js:84`). So every GoDaddy page view runs a Vercel function and a Neon query. When Neon has scaled to zero, that visitor waits for it to wake up.

Fix:

- Use `public, s-maxage=60, stale-while-revalidate=600` and drop the cache-buster. `docs/PUBLISH.md` already promises updates "within about a minute."
- Image ids change on every upload, so `/api/site-image/<id>` can be `public, max-age=31536000, immutable`.

### S9. Migrations run on every Vercel build (Low)

`npm run build` runs `scripts/migrate.mjs` against whatever `DATABASE_URL` the environment has, and Grok Build previews trigger builds. Keep Preview on its own Neon branch, or give it no `DATABASE_URL`. **Never** point it at production.

The same goes for Stripe: test keys on Preview, live keys on Production only.

### S10. Some queries are not scoped by chapter (Low)

These queries find rows by `event_id` without `chapter_id`:

- `listInvites` (`src/lib/crm/actions.ts:1244`)
- `exportNametags` (`actions.ts:2034`)
- the event lookups in `previewMail` / `sendMail` (`actions.ts:1848`, `1897`)

This is harmless with one chapter. Scope them anyway, so the new registration code copies the right pattern.

### S11. CSV exports are open to formula injection (Low, becomes Medium with public registration)

`exportNametags` wraps each cell in quotes (`actions.ts:2064`). That does not stop Excel from running a cell that starts with `=`, `+`, `-`, or `@`. Once strangers type their own names, put a `'` in front of any such cell in every export.

## 2. Website

### W1. Public pages are invisible to search engines and link previews

`/p/$slug` loads its content in the browser with `useEffect` (`src/routes/p/$slug/index.tsx:14-17`). So the HTML that Google, Facebook, LinkedIn, iMessage, and email clients receive says "Opening the page…".

Every page also shares one site-wide share card titled "Chapter Book" (`src/lib/og/site.json`), and there is no `public/og.jpg`. A texted link to the conference therefore shows "Chapter Book", with no conference title and no picture.

Fix, using TanStack Router's own tools:

- Load the page in a route `loader` so it renders on the server.
- Set a per-page `head()` with:
  - `title`, `description`, and `canonical`
  - `og:title`, `og:description`, and `og:image` (the venue photo or a speaker portrait)
- Add **schema.org `Event` JSON-LD** to the conference page:
  - `startDate` `2027-04-16`, plus `endDate` if Saturday is confirmed
  - `location`, `organizer`, `eventAttendanceMode`
  - once tickets exist, `offers` with price and availability

With that, Google can show the conference as an event result.

### W2. Give the book a chapter hostname before printing anything

The conference lives at `chapter-book-beryl.vercel.app/p/ai-conference`. A `vercel.app` address on a flyer, a QR code, or next to a card form looks less trustworthy than the chapter's own name.

Point a subdomain (for example `events.scs-wisconsin-usa.org`) at Vercel through Cloudflare. Then update:

- `BETTER_AUTH_URL`
- the CORS list in `public-cors.ts`
- the embed `<script src>` on GoDaddy

Do this **before** flyers, bulletin notices, and QR codes go out. Printed links cannot be changed.

## 4. Catholic particulars for April 15–17, 2027

**The liturgical calendar.**

- Easter 2027 is March 28, so April 15–17 fall in the **third week of Easter**.
- A Saturday evening Mass on April 17 would be the anticipated Mass of the **Fourth Sunday of Easter** (Good Shepherd Sunday). It satisfies the Sunday obligation for people who travelled in. Say so on the program.
- Holy Week is March 21–27, and many Catholic schools break the week after Easter. Set the school roster deadline before Holy Week, not after.
- Parish bulletins are crowded around Easter. Send bulletin notices for early March and again for April 4 and 11.

**Friday meals.** Outside Lent, US bishops allow another penance in place of Friday abstinence, but many attendees still keep a meatless Friday. Offer a good meatless main at Friday meals so no one has to ask.

**Mass at the venue.**

- If Mass will not be in a church or chapel, ask the chancery early. Mass outside a sacred place normally needs the local bishop's permission (can. 932 §1).
- Invite the local bishop now: his calendar fills 6–12 months ahead. Record the permission as a dated record, not a checkbox. The first review already flagged this for Gold Masses.

**Visiting clergy.**

- A priest from another diocese or order who will celebrate Mass or speak needs a **letter of suitability** from his bishop or superior, sent to the host diocese.
- With minors present, the host diocese will ask for it. Track: requested, received, and expires, on the person.

**Minors (high-school students).**

The chapter is a lay association, not a diocesan body. Still, the venue and the host diocese will expect their safe-environment rules to apply to any adult supervising minors at a Catholic event. Ask the diocesan safe-environment coordinator now. The book should hold:

| On | Record |
| --- | --- |
| Adult volunteer, chaperone, visiting clergy | Safe-environment training (program, date, diocese), background check date and expiry. Programs differ by diocese; many use VIRTUS, and the Archdiocese of Milwaukee runs its own |
| Minor's registration | "Under 18", grade, school, guardian name, email, and phone, emergency contact, optional medical notes, photo release yes/no, and consent signed by the guardian (typed name, date, time, version of the consent text), or paper consent marked received by an editor |
| School group | Lead chaperone, chaperone count against the ratio the school or diocese requires, roster deadline |

Practical rules:

- **Minors don't pay.** The purchaser is a parent, guardian, or school.
- **Collect only what the day needs.** "Under 18" and grade, not a birth date. Delete medical and emergency notes 30 days after the conference.
- **Photos:** don't publish identifiable minors without a photo release. Print a marker on the nametag (for example a colored dot) so photographers can tell.
- COPPA covers children under 13, so it doesn't apply to high-schoolers. Parental consent is still needed, for diocesan policy and liability.

## 5. Names, titles, and salutations

The name model is good: religious title, academic title, given, middle, family, and suffix. Two things break when mail goes out:

1. **Only one title prints.** When a person has both a religious and an academic title, the religious one wins and the academic one is dropped (`composedHonorific`, `src/lib/crm/lists.ts:119-124`). That is why "Rev. Dr." is in the list.

   Degrees are also seeded as *prefix* titles (`lists.ts:30`: "Ph.D.", "M.D.", "Sc.D.", "M.Sc."…). Picking "Ph.D." prints "Ph.D. Jane Doe".

   Split titles into a prefix (Rev., Dr., Sr., Br.) and **post-nominals** (Ph.D., S.J., O.P.). That gives "Rev. John Doe, S.J., Ph.D.", which is the right form for a priest-scientist.

2. **Salutations follow Catholic usage, not the title field.** Every seeded template begins `Dear {{honorific}} {{family_name}}` (`src/lib/crm/templates.ts:17` and nine others). That produces "Dear Most Rev. Smith" and "Dear Sr. Kowalski", both wrong.

   Add a computed **salutation** with a per-person override, and a `{{salutation}}` merge field:

| Title | Salutation |
| --- | --- |
| Most Rev. / Bishop | Dear Bishop Smith (formal: Your Excellency) |
| Cardinal | Your Eminence |
| Msgr. | Dear Monsignor Smith |
| Rev. / Fr. / Very Rev. | Dear Father Smith |
| Deacon / Dcn. | Dear Deacon Smith |
| Sr. / Mother | Dear Sister Mary Ann: women religious usually go by religious or first name, not surname |
| Br. | Dear Brother John |
| Abbot | Dear Father Abbot |
| Dr. / Prof. | Dear Dr. Smith / Dear Professor Smith |

The unsubscribe merge field is the literal text `(unsubscribe)` (`actions.ts:1639`). MAIL.md covers the fix.

## 7. `<section>` HTML on every public field

**Requirement:** every public-facing piece of copy can be entered as `<section> … </section>` HTML.

The sanitizer (`src/lib/crm/announcement-html.ts`) is sound. The trouble is that the book applies **two rules**, field by field:

- `publicRichHtml` accepts any allowed HTML. Page bodies, talk summaries, speaker pages, `/site` event cards, and the JSON feed use it.
- `announcementRichHtml`, and the embed's `safeSection` (`public/embed/chapter-site.js:75-81`), accept only a value that is one whole `<section>…</section>`.

Several fields use neither rule and print whatever is typed. A `<section>` typed there shows up on the page as literal tags.

| Public field | Edited in | Shown on | `<section>` today |
| --- | --- | --- | --- |
| Masthead "about" | Website → Masthead | GoDaddy (`data-scs="about"`), `/site` | **No.** The embed sets it with `textContent` (`chapter-site.js:93`) and `/site` prints it as text (`src/routes/site/index.tsx:77`) |
| Card summary: events, announcements | Website | GoDaddy cards, `/site` | **Partly.** Works on `/site`. On GoDaddy it works only when the whole value is one `<section>`; any other HTML falls back to plain words |
| Card summary: articles, documents, courses | Website | GoDaddy cards, `/site` | **Partly.** GoDaddy: only a whole `<section>`. `/site`: **no**, `CopyCard` prints it as text (`site/index.tsx:183`) |
| Page (detail body) | Website | `/p/<slug>` | Yes |
| Conference summary (hero) | Events → conference builder | `/p/ai-conference`, top of page | **No.** Printed as text (`src/components/conference-page.tsx:79`) |
| Conference body | Conference builder | Conference "About" | Yes |
| Talk summary and abstract | Conference builder | Talk cards, `/p/<talk>` | Yes |
| Notices (announcements tied to the conference) | Website | Strip on the conference page | **Partly.** Only a whole `<section>`; other HTML prints as text (`conference-page.tsx:112-123`) |
| Speaker biography | Conference builder | Speaker page: yes. **Lineup card: no** | The three-line excerpt on the lineup shows raw tags (`conference-page.tsx:199`). `biographyText` (`src/lib/crm/conference-page.ts:124`) doesn't strip them |
| Coming with registration: page intro, ticket descriptions, refund policy, consent text, "For schools", manage-page message, confirmation email | — | — | Build with `<section>` from the start (PAYMENTS.md, MAIL.md) |

**One-line fields** should stay plain text: titles, headline, when, where, audience, speaker role, button labels. They also feed the browser tab, share cards, event JSON-LD, email subject lines, Stripe line items, and nametags, where HTML cannot go.

If you want them to accept `<section>` too, the book can store the HTML and derive a plain-text copy (`announcementPlainText`) for those places. That is your call. The rest of this section assumes multi-line fields only.

**Recommendation:**

1. **One rule for every multi-line public field.** When the whole value is `<section>…</section>`, it is sanitized HTML. Otherwise it is plain text, and a blank line starts a new paragraph.
   - Keep accepting the bare HTML that existing page bodies already use, so nothing published breaks. The server wraps it in a `<section>`.
2. **One component: `PublicCopy`.** Use it for:
   - the conference summary
   - the masthead "about"
   - `CopyCard`
   - notices

   Excerpts, such as the lineup card, use the plain words (`announcementPlainText`) and are then clamped.
3. **Send sanitized HTML from the server, always wrapped in one `<section>`.**
   - The embed's `safeSection` check then passes for every card.
   - The feed gains `aboutHtml` for the masthead, rendered with the same check.
4. **Preview in the editor.** Give every such field a live preview, as the Website desk already does for summaries (`src/routes/website/index.tsx:560`), and the hint "Start with `<section>` for HTML."
5. **Safety,** so HTML can appear everywhere, the register page included: the tighter style list and `contain: paint` from S5.
6. **A test that covers every public field.** It feeds `<section><p>x</p></section>` into each one and fails if a literal `&lt;section` reaches a public page, the feed, or the embed.

**Verdict:** Chapter Book follows good CRM practice wherever it has chosen to go: clean entities, duplicate blocking on entry, an activity timeline, server-side roles, careful bulk mail, and event playbooks.

The gaps fall into four groups:

- **data-quality tools:** merge, import, full export
- **governance:** password reset, two-factor, audit log, retention, field privacy
- **consent and communication:** mail doesn't send, and consent isn't recorded
- **relationships:** dated clergy assignments, guardians, deceased

These are needed **before April**: consent, guardian relationships, audit log, two-factor, password reset, and merge. The rest can follow.
